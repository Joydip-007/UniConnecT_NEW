## Repo shape
- `apps/web` is the app itself (Vite SPA), not a standalone component library — no `dist`/`main`/`module` entry, no Storybook. The converter runs in **synth-entry mode** against `apps/web/src/components/**`.
- `pkg: "web"` is a monorepo-local package name that never gets self-installed under `node_modules/web`. A symlink at `apps/web/node_modules/web -> ..` stands in for it so `PKG_DIR` resolution works without `--entry` (passing `--entry` gets reused as the literal JS entry point, not just for locating `package.json` — don't do that here). Recreate the symlink on a fresh clone: `ln -sfn .. apps/web/node_modules/web`.
- `srcDir`/`tsconfig`/`componentSrcMap` paths in config.json are **PKG_DIR-relative** (i.e. relative to `apps/web`), not repo-root-relative — `cfgPath()` resolves via `resolve(PKG_DIR, rel)`.

## Styling — Tailwind, not shipped as static CSS
- Components use Tailwind utility classes with arbitrary `var(--token)` values (e.g. `rounded-[var(--r-pill)]`) — these only exist as real CSS after a Tailwind build, not from copying `tokens.css` alone.
- `cssEntry` points at `apps/web/.ds-compiled/tailwind-compiled.css`, a copy of the hashed `dist/assets/index-*.css` Vite produces. **Before every design-sync build, regenerate it:**
  ```sh
  cd apps/web && npx vite build && cat dist/assets/*.css > .ds-compiled/tailwind-compiled.css   # ALL chunks — see 2026-09-19 entry
  ```
  The hash changes every build — always re-copy to the stable filename `cssEntry` points at. `apps/web/dist/` and `apps/web/.ds-compiled/` are gitignored (build artifacts).

## Global providers wired in for all components
- `cfg.provider` wraps every preview in `<MemoryRouter><QueryClientProvider client={dsQueryClient}>...</QueryClientProvider></MemoryRouter>` — needed because `TopNav`/sidebars/`MinimalPageFooter` use `react-router-dom`'s `<Link>`/`useLocation`, and several components (`StickerDrawer`, `RightSidebar`, etc.) use TanStack Query's `useQuery`/`useMutation`.
- **Real bug hit and fixed once already**: `extraEntries` initially only had `"./src/ds-query-client.ts"` (the wrapper module exporting a `dsQueryClient` instance) but NOT `"@tanstack/react-query"` itself — so `QueryClientProvider` the component was never attached to `window.UniConnecT`, and EVERY preview in the bundle crashed with `Element type is invalid ... got undefined` inside the provider chain (confirmed via `grep -c "window.UniConnecT.QueryClientProvider" ds-bundle/components/*/*/*.html` matching all ~50 files). Fixed by adding `"@tanstack/react-query"` to `extraEntries` directly. **If adding another provider that needs a class/instance prop (not a plain JSON literal), always add BOTH the provider's own package name AND any small wrapper module to `extraEntries`** — the wrapper alone is not enough.
- `apps/web/src/ds-query-client.ts` is a 2-line file (`export const dsQueryClient = new QueryClient()`) added specifically for this — not part of the app itself, don't delete it as dead code in a future cleanup pass.

## Feature-component expansion (2026-07-17)

Expanded `srcDir`/`srcInclude` from the original 51-component `src/components/` library to also cover all 22 `features/*/components/` domains (211 components total). Three new config keys and two new forks make this possible — see `cfg.srcInclude`/`srcExclude`/`srcExcludeExports` in config.json and the `source-kit.mjs`/`common.mjs` fork entries in `cfg.libOverrides` for the mechanics (default-export re-export codegen, allowlist scoping so `main.tsx`'s top-level await doesn't enter the synth-entry, and same-name collisions across feature dirs like `EmptyState`/`TypeBadge`).

**Calibration (solo pass, 6 components across connections/mentorship/presence/groups domains) surfaced two systemic issues every subagent batch must handle:**

1. **TanStack Query data must be seeded on the SAME `dsQueryClient` singleton the provider uses.** Importing `dsQueryClient` via the `@/ds-query-client` path alias in a preview file gets a *different* esbuild-bundled module instance than the one `cfg.provider`'s `QueryClientProvider` actually renders with — `queryClient.setQueryData(...)` silently writes to a orphaned instance and the real component sees `isLoading: true` forever (renders `null`, blank card). **Always `import { dsQueryClient } from 'web'`** (the shared bundle export, not the path-aliased source file) when a preview needs to seed query cache before mount. Confirmed via `FeedbackSection` (`useRequestFeedback`/`useQuery(['mentorship','feedback', requestId])`) — blank until the import was switched from `@/ds-query-client` to `'web'`.
2. **Bare text/foreground-only cells render invisible on the preview card's white page background.** The app's default theme is dark (`--text-primary`/`--text-tertiary` resolve to light colors meant for a dark surface), so any preview cell that doesn't wrap its content in an explicit `background: 'var(--surface-page)'` div renders text that's technically present but effectively invisible against the card's white backdrop — passes `[RENDER_BLANK]`'s byte-size check (badges/icons still paint) but fails human review. This is NOT new — see `GhostBtn.tsx`'s existing `background: 'var(--surface-page)'` wrapper in the original 51 — it just wasn't consistently needed there since most of `src/components/` are self-contained cards/buttons with their own surface. Feature components lean more on bare text (badges without backgrounds, inline status labels), so **every new preview should default to wrapping its root in `<div style={{ padding: 12, background: 'var(--surface-page)' }}>`** unless the component already paints its own opaque background (e.g. `PointsBalance`'s card, which needed no wrapper and rendered correctly first try).

Subagent batch prompts for the remaining ~80 feature-component previews should state both of these up front — they are config-level/systemic, not per-component, so a subagent that hits either should NOT treat it as a one-off `.tsx` bug to work around differently per component.

### Systemic issue #3 (revised after verification): the real fix for blank Modal/portal previews was the reduced-motion shim, not `cardMode`

Five of six subagent batches independently hit blank captures on every `<Modal>`-based (portal) component and hypothesized the missing `cardMode: "single"` override (which was already applied to the literal `Modal` component) as the cause — plausible, since `cardMode: "single"` renders a full viewport instead of a cropped grid cell, and portal content is positioned relative to the real viewport. **The orchestrator applied that override to all ~24 affected components, rebuilt, and recaptured — they were STILL fully blank, including the plain `Modal` component itself**, which already had the override and had never actually been verified with a real screenshot (no `Modal.grade.json` existed before this session, despite NOTES.md previously claiming the override was "applied").

The actual root cause: `Modal.tsx` uses framer-motion `AnimatePresence` with `initial: reduced ? false : overlayIn.initial` (`opacity: 0` when not reduced), and the capture harness's `settle()` only waits for fonts/images — not animations — so every capture landed mid-transition at `opacity: 0`. **Fix**: shim `window.matchMedia` at the top of the preview module to report `prefers-reduced-motion: reduce` as `true`, forcing `useReducedMotion()` to return true and the component to skip its `initial` state, rendering already-settled. Applied to all ~26 affected preview files (`Modal`, `Drawer`, `ShareMenu`, `ImageLightbox`, and every component that wraps `<Modal>` or uses its own `createPortal`/`position:fixed` overlay with a `useReducedMotion()`-gated animation) — confirmed via fresh screenshots that this fixes the overwhelming majority (~20 of 24) of previously-blocked modals. The `cardMode: "single"` overrides were kept (harmless, and needed regardless so single-story captures aren't cropped to a grid cell), but they were not the actual fix.

**Any future preview for a `<Modal>`-wrapping or portal/fixed-position component MUST include this matchMedia shim** (see `Modal.tsx` or `ConnectionRequestModal.tsx` in `.design-sync/previews/` for the reference snippet) — this supersedes/extends systemic issue #4 below, which described the same shim for non-Modal components (`SearchPanel`, `MessagesPopup`) discovered independently in the pre-fan-out solo work.

## CRITICAL: the correct `--node-modules` value is `apps/web/node_modules`, NOT deeper

Discovered 2026-07-24 after an entire sync session run with the wrong value produced a silent, hard-to-notice bug: `--node-modules apps/web/node_modules/web/node_modules` (pointing one level "into" the `web` symlink stand-in, by analogy with normal monorepo packages where you'd point at the package's own resolved `node_modules`) **looks correct and mostly works** — component discovery, react/react-dom resolution, and the main bundle all succeed identically, because the `apps/web/node_modules/web -> ..` symlink is self-referential (`web/node_modules/web` loops back to the same real `apps/web` directory the OS resolves through, however many `/node_modules/web` segments you append). The bundle output is byte-identical either way.

**Where it silently breaks**: `cfg.extraFonts` (and any other `workspaceRoot`-bounded field) resolves via `resolve(PKG_DIR, rel)` — a purely LEXICAL/textual join with no symlink awareness, unlike the OS's real directory walk that `ls`/`fs.stat` do. The config's `../../../../.design-sync/fonts/...` values are hardcoded assuming `PKG_DIR = join(NODE_MODULES, PKG)` lands exactly at `apps/web/node_modules/web` (4 levels above real repo root). Passing the deeper `--node-modules` value shifts `PKG_DIR` two segments deeper, so the same 4 `../`s land two levels short of repo root — and `existsSync()` on that (still lexically valid-looking) wrong path just fails quietly: `! extraFonts: ... not found — skipped`. The build still succeeds (exit 0), so nothing forces you to notice — the DS pane would have silently shipped with system-font fallbacks instead of real Satoshi/JetBrains Mono, with no error anywhere in the pipeline.

**Always pass `--node-modules apps/web/node_modules`** (matching NOTES.md's "Repo shape" section above) for both `package-build.mjs` and `resync.mjs` in this repo. If a future validate run prints `[FONT_MISSING]` for Satoshi/JetBrains Mono despite `.design-sync/fonts/` clearly having the files, re-check this flag FIRST before assuming the font files themselves are broken.

## Seeding Zustand stores from a preview (resolves systemic issue #5)

`CreatePost`, `CreateEventForm` and `EditProfileModal` are no longer blocked. All three are authored and graded `good`.

**The real root cause was path identity, not "separate module graphs".** The synth entry reaches every source file by absolute path *through the `apps/web/node_modules/web` symlink*, and `tsconfigPathsPlugin` resolves `@/*` against that same prefix (`cfgPath(cfg.tsconfig)` is `<PKG_DIR>/tsconfig.json`, and `PKG_DIR` is the symlink). So components and their `@/`-alias imports share one module record. An `extraEntries` path does **not**: esbuild's own resolver realpaths it to `apps/web/src/...`, which is a textually different path for the same real file. esbuild dedupes by resolved path, so zustand's `create()` runs twice — that is where `useAuthStore2` came from. Nothing about zustand or context is special here; the same trap explains why a preview importing `dsQueryClient` from `@/ds-query-client` gets a different instance than the `'web'` export (2026-07-17 learning #1). One mechanism, two symptoms.

**The fix: re-export the store from inside the synth entry.** `apps/web/src/components/ds-auth-store.tsx` is one line, `export { useAuthStore } from '@/stores/authStore'`. Because it sits under an `srcInclude` prefix and is `.tsx` (the synth entry only walks `.tsx`/`.jsx` — a `.ts` file would be skipped), it joins the `export *` list and resolves through the same symlinked prefix as every component. Confirmed: the built bundle now contains exactly one `useAuthStore` identifier, and `CreatePost`'s placeholder greets the seeded user by name.

- Previews seed with `useAuthStore.setState({ user, isLoading: false })` — **never `setAuth()`**, which writes `localStorage` and opens a socket.
- The file exports nothing PascalCase, so discovery adds no component: the count stayed at 222.
- **This cost zero re-grades.** `srcInclude`-reachable source files are not in the grade key, so only the three edited preview files re-graded.
- **Why not fix `bundle.mjs` instead**: realpath'ing the plugin's returned path would fix the whole class, but `configSlicesFor` hashes fork file bytes into the *global* grade slice, so editing the fork invalidates all 222 grades at once. The re-export is the cheap equivalent. If a future sync needs the general fix anyway, budget the full re-verify.
- **Any other store a preview needs** (`themeStore`, `presenceStore`, …) gets the same one-line treatment: add it to `ds-auth-store.tsx` or a sibling `.tsx` under `src/components/`. Do **not** reach for `extraEntries`.

`CreateEventForm` needed one more thing beyond the seed: it is a bare `position: fixed; inset: 0` overlay, **not** portalled through `Modal` like `EditProfileModal`. Returned bare from a preview its root has no measurable height and the card crops to a ~40px sliver of the backdrop — and the `viewport` override alone does **not** fix it. It needs an explicitly sized wrapper (`position: relative; width/height`), the same remedy as `ChatView`'s `flex: 1` root. Note `viewport` *is* grade-keyed (only `cardMode`/`primaryStory` are stripped), so adding one trips `[CONFIG_STALE]` on a targeted rebuild and requires a full `package-build.mjs`.

### Follow-on: unblocking a component can surface a `[GRID_OVERFLOW]` it could never trip while blank

`CreatePost` had `cardMode: "column"` and was quiet for months — because its `EditModeOpen` story rendered nothing at all (the `if (!user) return null` gate). The moment the store seed made it render, its portal/fixed edit modal started positioning content outside its grid cell and validate flagged it. Changed to `cardMode: "single", primaryStory: "CollapsedTrigger"` (the canonical resting state). Expect the same class of follow-on warn whenever a previously-blank overlay component starts rendering for real — it is not a regression, it is the check finally having something to measure.
