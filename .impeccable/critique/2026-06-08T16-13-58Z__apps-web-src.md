## Overall Impression

The visual and interaction foundation is genuinely strong — one of the more disciplined design systems in a student-built product. The gaps are almost entirely in the *help layer*: shuttle controls that require trial-and-error to understand, admin features with no legend, and destructive actions that offer no recovery. The interface trusts users too much to figure things out unaided, which works for daily power users but will fail new faculty or infrequent alumni.

**Single biggest opportunity:** shuttle controls. Five unlabeled toggles on a page that already has a complex map is the most glaring friction point in the entire product.

---

## What's Working

1. **Token system is airtight.** Dark/light theme switch is seamless, color roles are semantically correct (orange = you, indigo = system/peers), and zero hardcoded hex anywhere in component code. This level of discipline is rare and pays dividends in every future change.

2. **Error messaging is specific.** LoginPage distinguishes unverified account from wrong password. Shuttle error state names the problem ("Couldn't reach the shuttle service") and provides a direct retry. No silent failures, no generic "Something went wrong."

3. **Compose flow is frictionless.** Instant-open on `c` key, auto-expanding textarea, inline poll builder, photo preview with cap, edit-mode pre-fill, draft discard confirmation. The full lifecycle of a post is handled cleanly in one surface.

## Priority Issues

### [P0] Shuttle controls cognitive overload
**What:** ShuttlePage exposes map/list view toggle, nearest/recent sort, LiveOnly filter, and FocusMode — all in a flat row with no hierarchy, no tooltips, and label names that don't describe behavior.  
**Why it matters:** "Focus mode" is meaningless without a tooltip. "Live only" could mean buses-with-GPS-only or currently-active-routes-only — users can't tell. The sort order (nearest/top/recent) also changes meaning depending on liveOnly state. Five decisions at once before the user even looks at the map.  
**Fix:** Rename "Focus mode" → "Show selected route only." Add hover/tap tooltips on LiveOnly: "Hide estimated-position buses." Collapse Sort into a popover instead of inline buttons. Add "Filters" affordance on mobile to group them.  
**Command:** `/impeccable clarify` + `/impeccable layout`

### [P1] No undo for destructive actions
**What:** Deleting a post, declining a mentorship request, and canceling a draft after confirmation have no recovery path. `window.confirm("Discard this post?")` was already replaced with a proper guard — but after confirming, the action is permanent.  
**Why it matters:** Mobile fat-finger risk is real. An accidental delete on a post with replies leaves the conversation broken. No recovery erodes trust, especially for alumni who draft carefully.  
**Fix:** Add a 5-second "Undo" toast after delete (soft-delete client-side, cancel the mutation if undo is clicked). Replace remaining `window.confirm` instances with a proper in-UI confirmation component that has explicit Cancel/Confirm buttons.  
**Command:** `/impeccable harden`

### [P1] Mentorship admin panel has no legend
**What:** MentorshipTab shows `mentorshipPoints`, capacity bars (orange at 100%, mint below), `completedCount`, `totalSessions` — none explained. An admin cannot answer "why did this mentor's points drop?" or "what does full capacity mean for students?"  
**Why it matters:** Admins set policy; if they can't explain the system to mentors, trust in the feature breaks. The points economy (POINTS_PER_SESSION = 10) is invisible to the UI.  
**Fix:** Add an "?" info button near the header → popover/modal explaining: points formula, capacity enforcement rules, session credit model. Annotate the capacity bar with labels ("At capacity" / "Has availability"). Show recent point events inline on expanded rows.  
**Command:** `/impeccable clarify`

### [P2] `transition: width` in 3 remaining components
**What:** `RadialOrbitalTimeline.tsx:228`, `AnimatedTabBar.tsx:53`, `OnboardingChecklist.tsx:103` all animate `width` directly, causing layout recalculation on every frame.  
**Why it matters:** On lower-end Android devices (common in Bangladesh campus context), layout thrash during animations produces visible jank. The MentorshipTab bar was already fixed to `transform: scaleX()` — these need the same treatment.  
**Fix:**
- `OnboardingChecklist.tsx:103`: Progress bar — replace `width: ${pct}%` + `transition: width` with `width: 100%` + `transform: scaleX(${pct/100})` + `transformOrigin: left center` + `transition: transform`.
- `AnimatedTabBar.tsx:53`: Active indicator — same pattern.
- `RadialOrbitalTimeline.tsx:228`: Inspect context; if it's a progress/fill bar, apply scaleX. If it's a layout container, consider `grid-template-columns` transition instead.  
**Command:** `/impeccable optimize`

### [P3] Shuttle stop affordances invisible on mobile
**What:** Route stop info is Leaflet `Tooltip` (hover-only). On mobile touch devices, there is no tap affordance — the stop marker is a dot with no visual cue that it's interactive. Clicking the route polyline to select it also has no affordance.  
**Why it matters:** This is a map-first feature for campus commuters who are mostly on mobile. If stops aren't tappable, the entire "stop ETA" feature is useless on the primary device.  
**Fix:** Replace Leaflet `Tooltip` with `Popup` for stop markers (tap-to-open behavior). Add a small tap-target ring on stop dots (min 44px touch area). Add a subtle "Tap route to select" label on first map load, dismissed after first interaction.  
**Command:** `/impeccable adapt`

## Questions to Consider

1. **Does "Focus mode" belong on the shuttle map at all?** If it just hides other routes, the route tabs already select a route. Is focus mode doing something meaningfully different, or is it redundant state that confuses more than it helps?

2. **Should mentorship points be visible to mentors themselves?** Right now only admins see the score. If mentors saw "+10 pts" after a session in their own profile, it would make the gamification legible and motivating — and would eliminate the admin explanation burden entirely.

3. **What happens to an archived post's comments?** The `archived_at` column exists, computed states include "archived" — but there's no UI for browsing your own archived posts, and no indication to readers that a post was archived vs. deleted. Is the archive for the author's drafts only, or does it affect public visibility?
