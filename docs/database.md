# Database

PostgreSQL 16 with the `uuid-ossp` extension. All IDs are UUIDs generated by `uuid_generate_v4()`. All timestamps are `TIMESTAMPTZ` defaulting to `NOW()`. There is no Postgres RLS — multi-tenant isolation (`university_id`) is enforced entirely in the service layer.

Migrations live in `apps/api/src/database/migrations/`, filename `NNN_description.ts` (sequential prefix). **Known quirks:** there are two `072_` files (`072_add_post_lifecycle.ts`, `072_add_username_to_users.ts`) and two `098_` files (`098_add_ai_quiz_settings.ts`, `098_add_skill_path_source_and_quiz_approval.ts`). Both are numbering collisions, left in place rather than renumbering committed migrations. Latest migration as of this doc: `120_learning_quiz_attempts_and_badge_pins.ts`. The next migration starts at `121_`.

```
                       tags, post_tags, polls, poll_options, poll_votes

                       group_study_sessions, group_announcements,

                       group_consultation_bookings, group_quizzes

                       group_shared_notes, group_session_creator_notes,
                       group_session_member_notes

                       course_outline_topics, gradebook_entries,
                       academic_group_modules, academic_assignments,
                       academic_submissions

                       message_reactions, message_user_states
Notifications & News → notifications, news
Campus Tools         → lost_and_found, lost_found_saves, courses, user_courses,
                       shuttle_routes, shuttle_locations, shuttle_shifts,
                       shuttle_rider_prefs, shuttle_notices
Engagement           → mentorship_requests, mentorship_sessions,
                       mentorship_session_requests, mentorship_waitlist,
                       mentorship_feedback, gift_cards, mentor_redemptions,
                       badges, user_badges, reports
Moderation            → user_blocks, user_mutes, account_deletion_requests,
                       problem_reports
Profile sections      → profile_experiences, profile_education, profile_featured,
                       profile_views
Settings & Push       → user_settings, push_subscriptions
Content sync          → content_sync_runs, content_attachments
                       (+ imported_* columns on news/events)
Learning platform     → skill_paths, skill_path_units, skill_path_enrollments,
                       unit_completions, learning_stats, daily_quiz_slots,
                       daily_quiz_attempts, ai_quiz_pool, unit_quiz_attempts
Audit                → university_audit_logs
Presence              → NOT a Postgres table — tracked entirely in Redis (see below)
```

**Presence note:** online/offline status is tracked in Redis only (`presence:count:{userId}`, `presence:online:{universityId}`), refreshed by socket heartbeats. `users.last_seen_at` (Postgres) is written only on the online→offline transition, as a durable "last seen" fallback. There is no `presence` table — do not look for one.

## Job Board

### `jobs`
Adds `is_published BOOLEAN DEFAULT TRUE` (migration 064, unified draft model), and from migration 116 `eligible_departments TEXT[]`, `eligible_batches TEXT[]`, `min_cgpa NUMERIC(3,2)` and `publish_at TIMESTAMPTZ` (a future value hides the job via the `isLive` query filter, with no worker involved), on top of the original columns: `title`, `company`, `location`, `type` (full_time · part_time · internship · remote · contract), `description`, `requirements TEXT[]`, `salary_range`, `application_url`, `deadline`, `is_active`, `view_count`, plus a generated `search_vector` (migration 070, weight A=title/company, B=location, C=description).

**Indexes:** `(university_id)`, `(is_active, deadline)`, `(university_id, is_published, created_at DESC)`, GIN on `search_vector`.

### `job_applications` / `saved_jobs`
`job_applications`: `UNIQUE(job_id, applicant_id)`, status pending·reviewed·shortlisted·interviewed·offered·rejected·withdrawn. `withdrawn` was added in migration 116 and is set only by `POST /jobs/:jobId/withdraw`. The eligibility rule is `evaluateJobEligibility()` in `@uniconnect/shared`.

`group_id`, `title`, `description`, `week_number`, `display_order`, `is_published`, `file_urls JSONB DEFAULT '[]'` (migration 101, uploaded via `POST /groups/:groupId/modules/upload-url`).

## Moderation (migrations 078–079)

### `user_blocks`
`blocker_id`, `blocked_id`. Stored directionally, enforced bidirectionally at the service layer (neither party can message, connect with, or see the other); blocking also tears down any existing `connections` row between the two. `UNIQUE(blocker_id, blocked_id)`, CHECK `blocker_id <> blocked_id`.

### `user_mutes`
`muter_id`, `muted_id`. One-directional and silent — muter stops seeing muted user's posts in feed; muted user is unaware. Distinct from `conversation_participants.is_muted` (which mutes a single chat thread). `UNIQUE(muter_id, muted_id)`, CHECK no self-mute.

### `account_deletion_requests`
UniConnecT is invite-based — no user self-delete. A member files a deletion request with a `reason`; admins review via `admin_note`/`reviewed_by`/`reviewed_at`. `status` CHECK IN (pending·approved·declined·cancelled). At most one `pending` request per user (partial unique index). Distinct from the reversible `users.deactivated_at` self-deactivation.

### `problem_reports` (migration 118)
Crash reports filed from the in-shell "This page didn't load" card. `user_id`, `error_id VARCHAR(16)`, `error_message`, `description`, `page_url`, `user_agent`, `status` CHECK IN (open·resolved), `resolved_by`, `resolved_at`. `UNIQUE(user_id, error_id)` makes a resend a retry rather than a duplicate. Admins work them at `/admin/problem-reports`.

## Migrations

```bash
# Create a new migration
npx pnpm --filter api db:migrate:make add_<description>

# Run all pending migrations
npx pnpm --filter api db:migrate

# Rollback last batch
npx pnpm --filter api db:rollback

# Full reset (dev only — destructive)
npx pnpm --filter api db:reset
```

### Migration file conventions
- Filename: `NNN_description.ts` — sequential number prefix (not a timestamp). Next available prefix is `121_`; check `ls apps/api/src/database/migrations | tail -1` before creating one.
- Location: `apps/api/src/database/migrations/`
- **Never edit a committed migration.** Create a new one that corrects it.
- **Fixing a broken `down()` is the one allowed edit** to a committed migration — no new migration can repair a previous migration's `down()`. Never touch a committed `up()`.
- A `down()` that narrows a CHECK constraint must drop the constraint, fold or delete the offending rows, then re-add it (see `047`, `073`, `092`, `103`, `111`). Verify the rollback with that hostile data present.
- Always write the `down` function to make rollbacks reliable — some migrations here deliberately make `down` a partial/no-op when the forward change is irreversible by design (e.g. migration 092's flashcard-data purge is explicitly not reversible; migration 077's `source_url` relaxation is left relaxed on rollback).
- For large tables (>100k rows), add new nullable columns and backfill in a separate migration or background job.
- Generated (`STORED`) columns must use only `IMMUTABLE` functions — migration 070 wraps the built-in `array_to_string` (which is only `STABLE`) in a custom `IMMUTABLE` SQL function (`immutable_array_to_string`) to satisfy this. Using a `STABLE` function directly in a `STORED` generated column crashes migrations at startup (see `docs/incident-070-immutable-generated-column.md`-style postmortems).

### Adding an index in a migration
```typescript
export async function up(knex: Knex) {
  await knex.schema.table('posts', (table) => {
    table.index(['university_id', 'created_at'], 'idx_posts_university_created');
  });
}
export async function down(knex: Knex) {
  await knex.schema.table('posts', (table) => {
    table.dropIndex(['university_id', 'created_at'], 'idx_posts_university_created');
  });
}
```
